# Proof, quality and delivery contract

## Absolute distinction

- *Installed dependency*: not proof of a figure.
- *HTML Hairline skill output*: not proof of React app integration.
- *React figure rendered*: not proof of interaction with application state.
- *Hover transform / simple reveal*: not proof of bespoke component redesign.
- *Screenshot*: not proof of motion performance or correctness.

## Evidence in every batch

- Changed React component paths and diff summary.
- Before/after screenshot **same browser, viewport, content** with corresponding routes.
- Short Playwright browser video of pointer and keyboard interaction, paused/reduced alternative where relevant.
- State transition trace: input -> scene -> associated explanation or code -> URL/deep link if appropriate.
- Actual Hairline figure source (if created), link from output study to integrated React module, explain public API integration or authored SVG/Motion alternative.
- Browser console and hydration error check.
- 320, 390, 768, 1024, 1440, 1920 px and 200% zoom.
- Contrast & visible focus, touch and keyboard parity, reduced motion, explicit pause for hero signal.
- Semantic product copy, accurate API examples and release status; no missing docs content.
- Lighthouse performance trend and production bundle analysis; avoid broad JS clientification, >3D/Canvas unless proven need.

## Hard fail patterns

1. Old layout with larger shadow / border-radius / fancy cursor.
2. Stock component demos pasted into the page without a meaningful relationship to AstraFlow.
3. Three different figures but each reacts to hover by merely translating Y -4px.
4. Fake integration: generated figure exists in `/experiments` but not used by app.
5. New visual language that replaces the real AstraFlow A or color grammar.
6. Fullscreen scroll-jacking or transitions that block navigation.
7. Motion loses state after fast clicking; code panel and flow do not match.
8. Fabricated package installation/version/status or false telemetry claim.
9. Inaccessible canvas with links hidden under SVG.
10. Passing tests against only static screenshots instead of user action outcomes.

## Rebuild acceptance checklist

- [ ] Eleven targets each replaced materially (composition + behaviour), not just cosmetically.
- [ ] Three first-priority sections (Packages Hero/Composer, Home Flow Atlas, Changelog) are implemented, recorded, visually reviewed, iterated.
- [ ] At least two original Hairline-style creative studies exist and winning results are integrated into **real routes**, OR a clearly justified custom SVG+Motion equivalent is presented with actual behavior and code.
- [ ] Home hero logo stays stationary, trace path alive, pause/reduced motion work.
- [ ] All meaningful scenes accessible with mouse, keyboard, touch.
- [ ] No regressions to Docs content, URLs, SEO, i18n/RTL foundations, theme tokens, real published releases.
- [ ] No hydration errors, horizontal overflow, stuck animation or mismatched state.
- [ ] Production build succeeds; Playwright interaction tests and visual evidence attached.

No invented score. Do not call it final because it looks similar to a concept image. If the first redesigned slice still resembles the old static figure, do not propagate it to the other routes; fix the creative execution first.
