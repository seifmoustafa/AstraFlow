## Follow-up hardening

Additional tests cover keyword identifiers, separate pairs, nullable destinations and missing types. With stable SDK 10.0.400, `dotnet test tests/AstraFlow.Generators.Tests/AstraFlow.Generators.Tests.csproj -c Release --no-restore /m:1 /p:UseSharedCompilation=false` passed 23 tests.

A runtime test confirmed SQLite 3.49.1 before the change. The test project now directly references bundle 2.1.12; its resolved bundle, provider and native library are 2.1.12, and all seven EF tests pass, including a check that the loaded SQLite is at least 3.50.2. The [advisory](https://github.com/advisories/GHSA-2m69-gcr7-jv3q) lists versions through 2.1.11 as affected; the [upstream maintenance release](https://github.com/ericsink/SQLitePCL.raw/releases/tag/v2.1.12) identifies its updated SQLite dependency. This override is test-only and does not change a public package dependency. Recheck the full solution restore and dependency audit before release.

### Preliminary mapping benchmark

The new `GeneratedMappingBenchmarks` compares one `int` and one `string` mapped to a newly allocated DTO. Its setup checks output equivalence; runtime uses a scoped `IMapper` and an explicit rule which calls the same hand-written mapping used for the manual baseline. The generated method is a direct typed call. No collection, startup, external mapper, compilation or AOT costs are represented. Runtime facade semantics differ in general, even though the values in this particular workload match.

On Windows 11 build 26300, .NET SDK 10.0.400, .NET runtime 10.0.13 x64, BenchmarkDotNet 0.14.0, three warmups and three measurements were run with `--filter '*GeneratedMappingBenchmarks*' --job short`. Raw logs are in [benchmark-results/v2.1-draft](../benchmark-results/v2.1-draft/). Two in-process runs observed manual means of 5.296 and 10.756 ns, runtime means of 103.519 and 137.221 ns, and generated means of 5.692 and 5.321 ns. A separate-process run observed 5.095, 83.776 and 10.609 ns respectively. All three reported 32 B per manual/generated call and 264 B per runtime call. The isolated manual estimate had a 99.9% error of 16.315 ns, larger than its mean; differences across runs and wide intervals make timing ratios unreliable. These short single-machine experiments do not support a speed claim. Run longer isolated jobs and measure cold start, build/incremental overhead and binary size before the performance gate is considered satisfied.

An exploratory build-cost run used two fresh net10.0 console consumers, stable SDK 10.0.400 and the local `2.1.0-local-d67455f` Mapper package. Both mapped the same sample DTO; the manual project used a handwritten method, while the generated project referenced the entire Generators package and declared the partial method. After restore, each of three iterations ran `dotnet build App.csproj -c Release --no-restore -t:Rebuild /m:1 /p:UseSharedCompilation=false -v:q`, then appended a comment to `Program.cs` and ran the same command without `-t:Rebuild`. Wall-clock milliseconds, in fixed manual-then-generated order:

| Iteration | Manual rebuild | Generated rebuild | Manual changed-file build | Generated changed-file build |
| --- | ---: | ---: | ---: | ---: |
| 1 | 3151 | 3394 | 2949 | 3442 |
| 2 | 3359 | 3545 | 2777 | 3484 |
| 3 | 3455 | 3455 | 3137 | 3648 |

All twelve builds exited 0 with zero warnings. This measures end-to-end process and MSBuild time on one machine with one mapping, a fixed order and only three samples. The generator package also contains existing metadata generators, so the difference cannot be attributed solely to the new generator. It does not measure many mappings, no-change builds, incremental Roslyn invalidation or cold start; it is not a general performance claim.

The tracked two-declaration Roslyn driver test confirms that an unchanged compilation reports the output step as cached. After editing one source property, Roslyn reports the single collected output step as modified, while the unaffected mapping's generated text and hint remain identical. The current `Collect()` design therefore reruns the output callback for the group on an edit; it does not demonstrate per-mapping cached emission. The test establishes invalidation behavior, not elapsed cost or scalability. Duplicate detection still scans declarations repeatedly, so a many-map profile and potential indexing change remain open.

At `5b33667`, a synthetic scale experiment built 25, 100 and 400 independent one-property class pairs with either hand-written methods or generated methods. The [script](../benchmark-results/v2.1-draft/map-scale-experiment.ps1) and [raw output](../benchmark-results/v2.1-draft/map-scale-results.log) record the workload and commands. Run from the stable SDK 10.0.400 selection directory after building Mapper and Generators. The recorded script differs from the original only in deriving the repository path from its checked-in location. Each scenario restored, then ran three Release `-t:Rebuild` builds with shared compilation disabled. All 18 builds succeeded with zero warnings and errors. Wall-clock milliseconds were:

| Pairs | Manual rebuilds | Generated rebuilds | Generated source bytes |
| ---: | --- | --- | ---: |
| 25 | 3650, 3382, 3636 | 5463, 19206, 6734 | 8785 |
| 100 | 4887, 3274, 4152 | 4326, 8293, 4625 | 35260 |
| 400 | 4686, 4544, 4303 | 6053, 5103, 6320 | 142360 |

The output consists of one generated file per pair. This is an end-to-end, fixed-order experiment on one machine; it includes process startup, compiler work and all generators in the assembly, and shows substantial timing noise. The manual and generated methods differ in their null checks. It cannot isolate duplicate scanning, establish a general scaling curve or measure incremental edits. The first trial failed because synthetic public types inherited XML documentation requirements; the recorded run uses internal types and did not suppress warnings. A focused generator profile and incremental-cost study remain open.

### Fresh local packages and consumer at d67455f

After the generator diagnostic changes, source commit `08ba66b` was packed again on stable SDK 10.0.400 with `dotnet pack` in Release and local-only version `2.1.0-local-08ba66b` for Mapper (all four TFMs) and Generators. The analyzer DLL inside the generator package and the built DLL both had SHA-256 `87FA0EC76346A8B7E57F05BC64C081BFAA94AC09E4A4E8DAA2E7E1A0EF6B66E0`; the generator package had no `lib/` assets. A fresh net10.0 PackageReference consumer using these packages and the generated mapping sample restored and ran, printing `Ada: 3`. `dotnet publish` with `-c Release -r win-x64 -p:PublishAot=true` succeeded, and the native executable also printed `Ada: 3`; no trim warnings appeared in the output. The first sandbox attempt could not write the global NuGet cache, and a workspace cache retry hit a long-path assembly error and NU1900 network warning. A short isolated directory and network-enabled retry succeeded. This validates one mapping shape and is not a substitute for final-source full package-family and release verification.

The public NuGet flat-container indexes reported `2.0.0` for both Mapper and Generators. The two current packages were packed with stable SDK 10.0.400 as local-only version `2.1.0-local-d67455f`. The generator package contained `analyzers/dotnet/cs/AstraFlow.Generators.dll`, no `lib/` assets, and its DLL SHA-256 matched the built DLL: `8A0815AFAE48CF49A33DF9312E6153C529E6C4D90C38C081E6F8704903F9D002`.

A fresh net10.0 consumer restored the local packages, emitted one mapping source and printed `Ada: 3`. `dotnet publish Consumer.csproj -c Release -r win-x64 -p:PublishAot=true --configfile NuGet.Config -o aot` exited 0; running the resulting `Consumer.exe` also printed `Ada: 3`, with no trim warnings in the output. This is evidence for this one shape and environment. The generated source was 400 bytes, the AOT executable 1,107,456 bytes, and the Generator and Mapper packages 438,954 and 569,906 bytes respectively; these sizes include the full sample/package contents and do not isolate generator overhead.

For each of the four Mapper TFMs, the package's documented XML member IDs were compared with published Mapper 2.0.0: none were missing, and the only added ID was `T:AstraFlow.Mapper.AstraGenerateMappingAttribute`. This is a documentation-ID comparison, not a complete binary or behavioral compatibility check. Repeat package/AOT checks after any code change and complete the broader package and API gates.
