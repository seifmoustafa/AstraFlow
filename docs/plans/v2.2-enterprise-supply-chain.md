# v2.2.0 — Enterprise Supply Chain Plan

> **Status:** Approved for implementation by the maintainer on 2026-11-02. The v2.1.0 source and GitHub release exist; NuGet publication remains a separate, currently unverified gate. This plan does not authorize package publication or merging.

## Outcome

Make each AstraFlow release traceable to reviewed source and a controlled build, make its package contents and dependencies inspectable, and give consumers verifiable source and signature evidence without introducing signing secrets into the repository.

## Current baseline

- `Directory.Build.props` already enables deterministic compiler output and repository metadata; CI must set `CI=true` explicitly and prove package reproducibility.
- GitHub-hosted .NET 8+ SDKs include Source Link for GitHub. Existing builds publish repository metadata and symbol packages, but CI does not verify source links.
- CI packs all 15 packages and automatically creates a GitHub release with unsigned package files and a generic release body.
- The manual NuGet workflow uses Trusted Publishing. NuGet.org repository-signs accepted package uploads; AstraFlow does not have a registered author-signing certificate. v2.2 will verify the repository signatures after publishing and will not claim author signing.
- CI does not generate a release SBOM or artifact provenance. Dependency review and maintainer guidance for security reporting and branch protection are absent or incomplete.

## Scope

1. **Source and deterministic package proof:** explicitly enable CI build metadata; verify Source Link URLs embedded in packaged PDBs resolve to the exact source commit; pack each package twice from the same Release outputs and compare package hashes.
2. **SBOM and provenance:** generate an SPDX SBOM from the packed release artifacts, upload it with the release, and create GitHub OIDC/Sigstore build-provenance and SBOM attestations for the release artifacts.
3. **NuGet signature verification:** after the gated Trusted Publishing workflow pushes packages, download each exact package version, run `dotnet nuget verify --all`, and fail if an uploaded package is not validly repository-signed. Preserve `--skip-duplicate` behavior while verifying duplicate versions against the immutable NuGet artifact.
4. **Signed release tags:** replace automatic unsigned tag creation with a keyless Sigstore/gitsign-signed annotated tag in the release job; verify the signature against the workflow identity and OIDC issuer before creating the GitHub Release.
5. **Dependency review:** add a least-privilege pull-request workflow that blocks newly introduced high or critical vulnerable dependencies. Keep its action version pinned and manageable through Dependabot.
6. **Release notes:** generate GitHub Release notes from merged pull requests and compare them with the manually maintained `CHANGELOG.md`; do not overwrite the canonical changelog automatically.
7. **Security and governance guidance:** document private vulnerability reporting, advisory response, recommended branch protection/status checks, signature and attestation verification, SBOM consumption, and the fact that GitHub repository settings still require maintainer configuration.
8. **Release metadata:** advance source/package version to 2.2.0, add a complete changelog entry, update the roadmap, release checklist, compatibility and publishing docs, and preserve the historical v2.1 evidence.

## Explicit exclusions

- No NuGet author-signing certificate, private signing key, or new long-lived secret is required. NuGet.org repository signatures are the package-signature mechanism for NuGet distribution; GitHub release artifacts are protected by build attestations.
- No application runtime API or package dependency changes.
- No automatic rewrite of `CHANGELOG.md`, hosted security service, or branch-protection API mutation.
- No claim that GitHub's UI displays gitsign tags as GitHub-verified GPG signatures; verification is performed with gitsign/Sigstore identity and transparency-log checks.

## Acceptance gates

- Full Release solution restore, build, and tests pass with the supported SDK matrix.
- All package projects produce deterministic `.nupkg` and `.snupkg` hashes on repeat pack from identical outputs.
- Source Link verification passes for every packaged PDB and verifies commit-pinned source URLs.
- One SPDX SBOM describes the complete release package set; every package and symbol artifact has a GitHub build-provenance attestation, and the SBOM itself is attached as an attested predicate to those package subjects.
- Dependency review passes on the repository PR and is configured as a required status check in the branch-protection guide.
- Release workflow creates and verifies a signed annotated tag and generates non-empty GitHub release notes.
- Post-publish signature verification passes for every NuGet package before the workflow reports success.
- Security policy identifies the supported release and an actionable private reporting path; release checklist distinguishes repository settings from code-controlled gates.
- CI, local package install, API compatibility, upgrade smoke, and sample builds pass; no secrets or generated package files are committed.

## Maintainer-controlled release gates

The maintainer must enable GitHub's Dependency graph, configure branch protection, and enable private vulnerability reporting in repository settings. NuGet Trusted Publishing must be corrected to the filename-only workflow claim and the `nuget` environment already used by the workflow. This implementation must not publish packages or create the v2.2.0 tag during review.
