# v2.4 — General-purpose Assertions Plan

> **Phase 1 implementation complete in source; package 2.4.0 is unreleased and pending release gates.** Build an original, AstraFlow-owned general-purpose assertion library for consumer test projects. Do not depend on, copy from, wrap, or expose another assertion package. This plan does not claim complete API parity or superiority.

The complete multi-phase 2.4.0 release scope is tracked in [the v2.4 release work plan](v2.4-release.md); the next approved phase adds safe enterprise shapes to executable generated mapping.

## User problem

Teams need expressive, high-quality assertions in their own .NET test projects. The current `AstraFlow.Testing` package solves a different problem: it supplies AstraFlow-specific fakes, harnesses, and focused assertions. The new library is for asserting behavior in any application, whether or not that application uses AstraFlow.

## Current baseline

- `AstraFlow.Testing` is a shipped, framework-neutral helper package for tests of applications using AstraFlow. It has no xUnit, NUnit, MSTest, FluentAssertions, or mocking-framework dependency.
- Before migration, an external assertion library was referenced only by AstraFlow's test projects: 14 test project references, with 548 `.Should()` usages across 18 C# test files in this checkout. No production `src/` project referenced it.
- The maintainer selected a clean-room implementation. No external assertion source, tests, implementation, package dependency, or API namespace is used by the AstraFlow Assertions package.

### Concrete call-site evidence

The 548 existing fluent assertion starts were counted in the 18 pre-existing C# test files, excluding the new assertion package's own tests. The most common chained calls are `Be` (131), `Contain` (124), `BeEmpty` (66), `ContainSingle` (47), `Equal` (26), `NotContain` (20), `ThrowAsync` (15), `BeTrue` (13), `BeOfType` (10), `HaveCount` (8), `BeSameAs` (7), `Throw` (7), and `BeFalse` (7). This is a useful demand sample, not a compatibility specification: it reflects AstraFlow's internal tests, not the full .NET ecosystem.

The audit also found predicate-based `Contain` and `NotContain` calls, and exception message pattern checks. Those are now included in the initial API; message matching uses ordinal, case-sensitive `*` and `?` wildcards and deliberately omits message contents from assertion failures. This narrows known gaps in AstraFlow's own common test vocabulary without claiming source compatibility.

### Internal migration evidence

The internal migration now replaces all 548 audited fluent call sites across the 18 pre-existing C# test files. Fourteen existing test projects use an AstraFlow.Assertions project reference; the package's own test project is the fifteenth. No test project retains an external assertion-package reference. This migration is a useful internal consumer audit, not a guarantee of broad source compatibility.

## Product boundary

Keep the responsibilities distinct:

| Package | Audience | Responsibility |
| --- | --- | --- |
| `AstraFlow.Assertions` | Any .NET test project | Original general-purpose value, object, collection, exception, and async assertion APIs. It must not require AstraFlow runtime packages, external assertion packages, or a particular test runner. |
| `AstraFlow.Testing` | Tests for apps using AstraFlow | AstraFlow-specific mediator fakes, handler/pipeline harnesses, mapper/projection/diagnostics assertions, and deterministic test helpers. |

Do not expand `AstraFlow.Testing` into a general assertion framework by adding the mediator, mapper, and diagnostics dependency graph to every consumer that only wants assertions.

## Chosen implementation boundary

Implement `AstraFlow.Assertions` from original AstraFlow source with no `PackageReference` entries in the production project. Do not copy or adapt external implementation or tests. Keep its namespace, assembly and public API AstraFlow-owned. Tests may use a test runner, but the shipping assertion assembly must not depend on any test framework or assertion library.

## Phase 1 capability boundary

| Capability | Initial surface | Explicitly not claimed yet |
| --- | --- | --- |
| Values and objects | Equality, inequality, inclusive comparisons/ranges, null checks, reference identity, exact runtime type and assignable type; explicit true/false, GUID, defined-enum and flag checks | Structural graph comparison, custom equivalency rules, nested property paths |
| Strings | Ordinal equality, contains, prefix/suffix, empty and whitespace checks | Culture-sensitive modes, regex, globbing, rich diff rendering |
| Sequences | Empty/non-empty, count, value and predicate membership, ordered equality, one matching item, key lookup on key-value-pair sequences, and predicate constraints | Set/multiset equivalence, rich per-item assertion scopes |
| Dictionaries | Key, key/value, value and count checks over `IDictionary<TKey,TValue>` | Read-only-only and specialized collection interfaces, duplicate policy configuration |
| Exceptions | Expected synchronous/asynchronous action or function exception type, no-throw checks, and message patterns | Inner-exception/property chains, timeout and cancellation policies, async enumerable assertions |
| Failure output | Stable diagnostic text; arbitrary object formatting and string content are omitted by default | Configurable global formatting, terminal color and source-expression capture |

The usage model is ordinary application testing: call a unit or service, then assert on its public result or observable side effects. The assertion package does not create fakes, run application code, choose a test runner, or validate AstraFlow internals. Those remain separate concerns.

## Capability expansion after the foundation

The full product goal is a practical replacement for common assertion workflows. The v2.4.0 first phase establishes the package, behavior rules, common assertion vocabulary, and consumer boundaries; it does **not** complete that replacement. Track broader capabilities as separate slices with tests before claiming coverage:

### Full capability inventory

The target surface is organized by capability rather than another library's method names. This is behavioral scope, not a promise to clone its syntax or internals.

| Family | Target capability | Scope and verification required |
| --- | --- | --- |
| Core values | Equality, identity, nullability, booleans, strings, GUIDs, enums, runtime type checks | Culture and comparer rules; null/value-type cases; useful failure context without leaking values |
| Numeric and temporal values | Integral/floating/decimal boundaries, precision and tolerance, nullable values, dates, offsets and durations | NaN/infinity, overflow, negative/zero tolerance, timezone offsets, precision edges and culture invariance |
| Sequences and dictionaries | Counts, ordering, membership, subsequences, set/multiset semantics, key/value rules and lazy/asynchronous streams | One-shot enumeration, disposal, duplicate values/keys, ordering and async cancellation |
| Object graphs | Structural comparison with selected/ignored members, nested paths, custom comparers, records, polymorphism and cycles | Mismatch path quality, recursion caps, cycle behavior, collection ordering, nulls and deterministic output |
| Exceptions and async execution | Type, message, inner/property chains, cancellation, completion/timeout and async-stream failures | Sync/async parity, no-completion, cancellation ownership, aggregate exceptions and secret-safe messages |
| Framework and structured data | XML, HTTP responses, streams/files, assemblies, types/methods/properties | Keep optional platform and parsing integrations isolated; verify disposal and malformed input |
| Runtime observation | Event monitoring and elapsed-time assertions | Unsubscription, event ordering, deterministic clocks where possible, timing flake policy |
| Language and authoring | F# ergonomics, assertion scopes, source/subject identification, extensibility and failure rendering | No test-runner requirement in the core; concurrency safety; stable scoped configuration and extension boundaries |

Completion of the replacement goal requires a disposition for every row: implemented with positive/negative tests, explicitly deferred with user-facing limits and roadmap ownership, or rejected with a recorded reason. No row is counted as supported from documentation or API-name resemblance alone.

| Capability family | Later capability work | Exit evidence |
| --- | --- | --- |
| Scalar and nullable types | Nullable values, numeric precision/approximation policies, dates, times and durations | Boundary tests, culture-independent behavior, overflow/precision cases |
| Collections and dictionaries | Ordering/subsequence, set/multiset, richer read-only dictionary APIs, duplicate and async-stream assertions | One-shot/lazy enumerable behavior, disposal, ordering and duplicate negatives |
| Object graphs | Structural equivalence, nested paths, selected/ignored members, cycles, recursion limits, custom comparers | Deep mismatch diagnostics, cycles/depth, collections, records and null graph cases |
| Exceptions and async work | Message/inner/property chains, timeout and cancellation policy, async streams | Sync/async parity, cancellation, wrong exception and no-completion cases |
| Specialized values | XML, HTTP responses, files/streams, events and elapsed time | Framework integrations remain optional; dedicated consumer tests for each supported target |
| Author experience | Assertion scopes, expression/source names, extensibility, improved diffs and IDE navigation | Deterministic messages, no secret leakage, stable public API and useful migration tooling |

Do not move all of these into one release merely to claim parity. Promote each family only after its semantics, API compatibility, negative cases, target coverage and clean consumer are reviewed.

## Phase 1 proposal for v2.4

1. Establish package identity, supported target frameworks, public namespace and test-runner-neutral exception behavior.
2. Implement a coherent first useful surface: equality and identity, nullability, type checks, strings, collections, synchronous exceptions, and asynchronous exceptions.
3. Add original positive and negative tests for each public assertion family, including deterministic and privacy-conscious failure messages.
4. Validate clean consumers and the package asset graph without adding any production dependencies.
5. Document the current surface, gaps, migration approach and compatibility policy. Keep mocks, fixtures, snapshots and test-runner adapters out of scope.
6. Expand the API in later phases based on user demand and conformance evidence; do not claim full parity from the first phase.

### Acceptance gates

- The package builds for its declared target frameworks and has no production `PackageReference`, AstraFlow runtime dependency, or test-runner dependency.
- Every shipped public assertion has positive and failure-path tests; unsupported categories and semantics are explicit.
- Equality, string, collection, type, exception and async exception failure messages are useful, deterministic and do not call arbitrary object `ToString()` by default.
- A clean local-feed package consumer compiles and runs without a test runner; the package can be used from a consumer's selected test runner without runner-specific code.
- `AstraFlow.Testing` remains independently installable and keeps its current package boundary unless a separate measured benefit justifies a dependency.
- Public API, package-asset, compatibility, and upgrade checks pass before publishing. No benchmark or “better than” claims in Phase 1.

### Exclusions and stop conditions

- No dependency on, code reuse from, or public reference to another assertion package.
- No claims of being better, faster, or fully compatible with any other assertion API in Phase 1.
- No test-runner replacement, mocking library, snapshot-test framework, or application test harness beyond existing AstraFlow-specific helpers.
- No claim of complete source compatibility until independently defined API and behavioral conformance evidence exists.
- Stop or narrow the release scope if the original API cannot be maintained across supported targets, or if clean consumer and failure-message quality gates cannot be met.

Later work may add AstraFlow-specific assertions and improvements after adopters identify gaps. That is a separate phase with its own acceptance criteria.
