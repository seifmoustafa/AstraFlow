# v2.5 — Assertions Capability Expansion (Candidate)

> **Candidate only; not approved for implementation or committed to a release.** The 2.4.0 assertion ship set is published as part of AstraFlow 2.4.1. This plan organizes deferred assertion work beside the existing v2.5 Flow Intelligence candidate without making either track a dependency of the other. The separate 2.4.2 and 2.4.3 compatibility patches address consumer-reported migration gaps and do not promote this candidate plan.

## Outcome

Continue AstraFlow's runner-neutral assertions package with a small number of high-value, behavior-defined improvements selected from adopter needs and the private capability inventory. Measure usefulness by successful consumer migrations and fewer unsupported test shapes, not by API count or name matching.

## Release placement

| Release | Assertions scope | Rule |
| --- | --- | --- |
| 2.4.0 | The already verified assertion and generator ship set | Do not add candidate features while preparing the local release. Only fix a proven 2.4.0 release blocker before the release is cut. |
| 2.4.1 and later 2.4.x | Regression fixes, consumer-proven migration compatibility overloads, documentation corrections, and release hardening | Do not add new assertion capability families. Skip a patch release when there is no verified fix or compatibility gap to ship. |
| 2.5.0 | A candidate additive assertion wave, alongside or separately from the independent Flow Intelligence candidate | Select only slices with demonstrated user value, approved contracts, and complete evidence. If a slice misses the scope freeze, move it to the next minor; never squeeze it into a patch. |
| 2.6.0+ | Broader specialized assertion families and adoption-led improvements | Reprioritize from consumer evidence. No feature is scheduled merely because it appears in the inventory. |

## Candidate 2.5 work, in priority order

These are discovery and implementation candidates, not promised APIs. Start with evidence review and approve each slice separately. Keep the 2.5.0 assertion wave to one or two independently shippable slices; do not fill the release with low-evidence parity work.

### 1. Async-enumerable completion and failure semantics

Design timeout and expected-failure behavior for finite and non-terminating async streams. Specify before choosing names or overloads:

- How timeout, caller cancellation, producer cancellation, producer failure, and normal completion differ.
- Who owns cancellation and enumerator disposal, including early exit and timeout.
- How late producer faults are observed without hanging or leaking work.
- Whether positive and negative completion checks enumerate once and what happens after partial consumption.

Require tests for normal completion, expected and unexpected producer faults, never-ending sources, cancellation races, timeout boundaries, disposal, late faults, and value-safe diagnostics. Keep stream APIs on the targets that support `IAsyncEnumerable<T>` without adding a package dependency.

### 2. Behavior-verified CLI migration rows

Expand the read-only `astraflow assertions analyze` mapping catalog only for calls whose exact bound symbol and behavior are tested against AstraFlow's implementation. Prioritize mappings from real consumer migration evidence. Keep lookalikes manual, unresolved calls unknown, and unsupported semantics explicit. Do not rewrite source or claim complete migration coverage.

## Later review queue for 2.6.0+

- Further structural-equivalency diagnostics and graph edge cases where consumer feedback identifies a concrete gap.
- Exception-property checks and less common specialized families such as path-based file assertions, broader reflection metadata, and richer timing or failure rendering.
- Additional collection contracts only where actual consumer shapes justify distinct, non-ambiguous public APIs.
- Further read-only dictionary work only if consumer evidence reveals a gap beyond the key, value, count, and mapping checks already included in the 2.4.0 candidate.

The inventory is a research aid, not a feature checklist. Unselected rows remain deferred or may be rejected after review.

## Relationship to Flow Intelligence

The [v2.5 Flow Intelligence candidate](v2.5-flow-intelligence.md) is an independent product track. Its manifest and diff work does not depend on Assertions API expansion, and the assertion work does not depend on the manifest. At v2.5 scope freeze, promote one or both tracks only if each has a named owner, bounded contract, user outcome, and passing acceptance gates. If both are too large, release the completed track and move the other to a later minor version.

## Acceptance gates for any promoted slice

- Record the user scenario and evidence that the current 2.4.0 API cannot serve it cleanly.
- Specify success, failure, null, cancellation, ordering, comparer, enumeration, lifetime, and diagnostic behavior before adding public members.
- Add positive, negative, boundary, privacy, and one-pass/disposal tests as applicable.
- Preserve the four current Assertions target frameworks unless an explicit compatibility decision is approved.
- Pass API-baseline, compatibility, clean packed-consumer, sample, and upgrade checks for the affected package surface.
- Update `CHANGELOG.md`, `docs/assertions.md`, README examples, package guidance, and synchronized portal content only for implemented and verified behavior. Keep future candidate work out of product documentation and the portal.
- Keep `AstraFlow.Assertions` dependency-free and independent of `AstraFlow.Testing`, validation integrations, and test runners.

## Stop conditions

Defer a slice if its semantics depend on hidden global state, ambiguous overload selection, arbitrary object formatting, unsafe cancellation ownership, or unverified equivalence assumptions. Do not start the next slice until the current one passes its evidence gates and is reflected accurately in the public docs.
