# v2.3.0 — Public API Governance

Status: completed in the published `2.3.0` release per maintainer confirmation on 2026-11-10; package-specific publication and hosted release-gate evidence should be checked independently where required.

## Repository evidence and decision

Before this release, AstraFlow had a pre-publish PowerShell check that downloaded a selected NuGet version and compared XML documentation member IDs. It was useful for detecting removals but did not keep an auditable baseline in the repository, did not fail ordinary pull request CI, and could skip comparisons when packages were missing.

v2.3 keeps that historical published-package check and adds a checked-in baseline for each XML-documented library target. CI compares build output against `docs/api-baselines/<project>/<tfm>.txt`. The explicit `scripts/update-public-api-baselines.ps1` command is the only automated writer. Baseline changes and code are reviewed together.

This reuses the documentation IDs already emitted by every library build, requires no new runtime or analyzer dependency, is deterministic, and makes an ordinary build produce readable diffs. The CLI project disables XML documentation because it is a tool rather than a library; its commands and output are covered by CLI contracts/tests.

The baseline represents XML documentation member IDs, not the complete CLR or nullable API contract. It catches documented symbol identity, including most parameter/type signature changes, but does not capture parameter names, nullable metadata, behavior, or undocumented members. CI therefore keeps `TreatWarningsAsErrors`, existing consumer tests, and the historical package comparison; human API review remains required. Replacing this with a full binary/nullable surface tool is a future decision if evidence shows that the remaining gaps cause material risk.

## Scope

- Establish and enforce a baseline for each target framework of every XML-documented source package.
- Test that the verifier passes unchanged baselines, fails on API drift, and updates baselines only when explicitly requested.
- Require a replacement name in every `Obsolete` message and enforce that rule in CI.
- Require changelog classification for breaking changes, additions, changes, fixes, deprecations, removals, and security work.
- Document API review, SemVer, release branch, obsolete API, and support-window policy.
- Keep compatibility comparisons and package-install/upgrade verification as separate release evidence.

## Acceptance gates

- A library API ID added, removed, or lost on one target causes `verify-public-api-baselines.ps1` to fail.
- The baseline update command writes a reviewed per-target diff and CI never updates baselines.
- A missing baseline or missing target XML documentation fails the gate.
- An `Obsolete` attribute without actionable replacement guidance fails CI.
- The changelog verifier requires all seven release categories.
- Existing public APIs, package boundaries, tests, and package behavior remain unchanged.
- Release build/test, package install, compatibility, upgrade smoke, sample build, and API gates pass before the PR is Ready for Review. Environment-blocked gates must be listed explicitly.

## Not included

- Removing or changing existing public APIs.
- Declaring a NuGet publication or release tag.
- Claiming that XML member-ID baselines are a complete binary compatibility proof.
- Adding a new analyzer or runtime dependency solely to implement governance.
