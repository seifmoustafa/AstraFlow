# v2.1.0 — Generated Mapping Execution: Implementation & Release Contract

> **Status: Proposed, not implemented.** One release, one primary objective. A public API is not committed until ADR-0001's source-level spike is approved. **Owner:** maintainer assignment pending.

## 1. Success definition

A clean external consumer explicitly declares a simple map and *runs* deterministic generated C# conversion, receives useful compiler diagnostics for unsupported/unsafe declarations, and can still use the existing explicit mapper and opt-in conventions unchanged.

The initial deliverable is **not** full AutoMapper/Mapster/Mapperly parity, not a new config DSL and not a performance claim. It is a credible end-to-end vertical slice that future mapping scenarios can safely extend.

### What ships if successful
- One minimal declaration mechanism chosen from actual repository API analysis.
- Real typed compiled mapping method for accessible, statically assignable scalar properties.
- Stable source-located diagnostics for unsupported construction/member/nullability/sensitivity cases.
- Generated source readable in IDE/compiler artifacts; deterministic tests.
- Documented interaction with existing mapper; optional adapter only if compatible with duplicate-pair rules.
- AOT clean app publish/run, fair benchmark artifacts, migration sample and release documentation.

## 2. Repository-first discovery (gate G0)

Before changing public code:
- Pin main SHA and check tag, source `Directory.Build.props`, GitHub Release and actual NuGet separately.
- Inspect `AstraFlow.Mapper` mapping interfaces, ownership and service lifetimes; `AstraFlow.Mapper.Conventions` policies; `AstraFlow.Generators` discovery/emission; `AstraFlow.Analyzers` diagnostic IDs.
- Inspect benchmark project, CI and scripts; use existing restore/build/test/pack/install/samples/API-diff commands **with verified flags**.
- Record what passed and failed *before* any feature work. Baseline failures must not be hidden as new regressions.
- Prototype method declaration vs pair declaration; decide a single API and publish ADR addendum.

**Exit artifact:** `docs/decisions/v2.1-source-audit.md` (proposed new path when implementing) with SHA, inspected concrete source types, rejected alternatives, exact API, supported subset, analyzer ownership and unresolved risks.

## Concrete baseline risks from current mapper code

At base SHA `d078e34`: [runtime mapper](../../src/AstraFlow.Mapper/AstraFlowObjectMapper.cs) has assignable-source identity return, collection handling before mapping-rule lookup, and zero/multiple-owner exceptions. [DI registration](../../src/AstraFlow.Mapper/AstraFlowMapperRegistration.cs) wires mapping rules as scoped; [generator](../../src/AstraFlow.Generators/AstraFlowMapperMetadataGenerator.cs) uses compilation-wide `CompilationProvider.Select`.

Before implementation, explicitly decide whether generated **direct** mapping is allowed to construct a fresh destination in cases where `IMapper` would return an assignable source unchanged. If so, don't claim those paths are behaviorally equivalent. Include identity/collection precedence test cases if an `IMapper` adapter is considered. Profile incremental rebuild cost rather than assuming existing generator infrastructure is granular.

Stop at each failed gate and either fix or reduce scope. Do **not** silently redefine unsupported features as supported.

## 5. Performance experiment specification

**Hypothesis:** the generated typed path can reduce some runtime mapping overhead while improving inspectability. It may increase build time and emitted IL.

Run in the same process/toolchain where possible:
1. Handwritten mapping baseline.
2. Existing AstraFlow explicit mapping.
3. Existing AstraFlow convention mapping (separately labeled).
4. New generated typed method.
5. New generated adapter through `IMapper`, **only if implemented**.
6. Relevant baseline versions of AutoMapper, Mapster and Mapperly; same destination semantics, ignore unsupported or non-equivalent modes rather than guessing.

Measure single DTO, simple collection and cold-start paths only where functionally comparable. Capture mean/distribution, allocs/op, throughput, CPU/GC, compiled code size, clean and incremental build time, generator memory if measurable, sample complexity and AOT output. State when a competitor cannot support a specific scenario on equal terms.

**No speed leadership claim** before multiple repeatable runs with raw result artifacts and precisely identified versions/environment.

## 6. Security and failure pre-mortem

- **Generated code silently copies secrets:** block sensitive destinations by default; tests explicitly attempt leakage.
- **An incomplete mapping compiles:** required-member and constructor correctness checks are release blockers.
- **Runtime DI rules conflict:** generated adapter is optional/deferred rather than bypassing registration checks.
- **Compiler cost explodes:** cap generation scope and benchmark changed-file recompilation; postpone nested graphs.
- **AOT smoke is misleading:** run published executable, review trim warnings and behavior, not just publish return code.
- **API churn:** narrow first declaration and require public API baseline review before extension points.
- **Large support matrix:** only promise tested TFMs/compiler combinations.

## 7. Out of scope — enforce this boundary

Generated mediator dispatch, automatic reverse mapping, complex inheritance/polymorphism, arbitrary dynamic resolvers, runtime profile DSL compilation, EF SQL generation, full collection-graph optimizers, cross-process messaging, web UI, IDE plugins, auth, job systems.

Records/immutable destinations are *stretch* only after base gates; they must not delay the first validated vertical slice.

## 8. Release checklist and stopping rule

- Restore, Release build, full tests, pack, clean install, sample builds and API diff pass on documented environment.
- Package analyzer/generator assets verified; determinism and negative tests green.
- Clean sample runs; AOT published executable runs.
- Public API docs, migration example, limitations, changelog and support/compatibility notes updated.
- Benchmarks include manual and current-runtime baselines and disclose costs.
- A concise completion report lists code SHA, changed files, public symbols, exact commands/results, test matrix, benchmark environment/raw artifacts, known exclusions, security assessment and maintainer decisions.

**After review: stop. Do not automatically proceed to v2.4 or broaden v2.1 mid-release.**
