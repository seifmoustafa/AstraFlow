# v2.5 — Explainable Flow Intelligence Candidate Plan

> **Candidate, not shipped.** Depends on stable CLI/diagnostics metadata and explicit maintainer promotion.

## Developer outcome

From a before/after code change, a reviewer can see **what is known to have changed** in handler registrations, pipeline order, mapping pairs or projection declarations; every assertion has provenance and unknown/dynamic behavior is highlighted, not silently omitted.

## Implementation sequence

1. Audit current CLI `inspect`, `report`, `diff` and `graph` models; reuse before adding new endpoints.
2. Propose a versioned JSON schema: stable node IDs, relation kinds, provenance, confidence, completeness and diagnostic references.
3. Emit deterministic registration/pipeline/mapping/projection facts with source origin where available.
4. Implement semantic diff: changed owners, order, added/removed mapping pairs and security-relevant changes; classify uncertain edge drift without false alarms.
5. Demonstrate one meaningful pull-request report in a clean consuming application, including a partial/incomplete assembly case.
6. Test redaction, stability under source-order changes, schema compatibility and bounded cost.
7. Produce human Markdown and machine JSON/SARIF where appropriate. Visual tooling only after positive demand.

## Non-goals

No arbitrary whole-program control-flow proof, payload tracing, web dashboard, hosted service, IDE plugin, compliance certification or claims that the absence of an edge proves no runtime execution.

## Acceptance

Two identical inputs produce identical artifacts; unknown relationships are clearly labeled; no secrets or payload values; schema has upgrade policy; users find at least one real change easier to review than without the tool. See [ADR-0003](../adr/0003-flow-manifest.md).
